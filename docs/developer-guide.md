# OSM engine developer guide

This guide is for developers who change `smartmet-engine-osm` or use it from a plugin,
and for administrators who install the map data.

The engine serves vector tile datasets, typically OpenStreetMap basemaps, from
[PMTiles v3](https://github.com/protomaps/PMTiles) files or from PostgreSQL, and renders them server side
with [MapLibre styles](https://maplibre.org/maplibre-style-spec/). The WMS/Dali plugin's
`OSMLayer` uses it for map backgrounds and for vector tiles in OGC API - Tiles; an OGC
API - Maps service can use the same calls.

[CLAUDE.md](../CLAUDE.md) has the architecture summary.

## 1. Building and testing

```bash
make
make test              # PMTiles reader hardening and dataset tests (test/*Test.cpp)
OSM_TEST_DB="host=127.0.0.1 port=5432 dbname=osm user=osm" make test   # also PostgreSQL
make -C test render    # development tool: render a map without a server
```

The PostgreSQL test creates and modifies the schema `osm_test` in the given database.

The test fixtures in `test/data` are generated by `test/make_fixtures.py` with the small
PMTiles writer `test/pmtiles_writer.py`. The tiles are not real vector tiles, each one
just names its file and coordinates so that the tests can check which file answered.

The render tool prints the time used and writes SVG to standard output:

```bash
test/render <datadir> <styledir> <dataset> <style> <crs> <x1,y1,x2,y2> <width> <height> [repeat]
test/render /smartmet/data/osm styles protomaps meteo-light EPSG:3067 \
    -600000,6100000,1100000,7900000 800 847 3 > map.svg
```

`OSM_CONFIG_EXTRA` adds settings to the configuration of the tool, for example
`OSM_CONFIG_EXTRA='file_access = "pread";'` or a `postgresql` group.

The WMS plugin tests cover rendering more widely, see `plugins/wms/test/osm/README.md`.

## 2. Data

The data is never packaged: OpenStreetMap data is licensed under the ODbL, and a planet
file is about 140 GB. The engine serves whatever is in its data directory:

```
/smartmet/data/osm/                  the configured directory
  protomaps/                         a dataset: all its files share one tile schema
    planet.pmtiles                   the whole world, zoom 0-15
  other.pmtiles                      a file directly in the directory is a dataset too
```

The recommended data is the [Protomaps basemap](https://docs.protomaps.com/basemaps/downloads),
built daily from OpenStreetMap (and Natural Earth for low zoom levels) with Planetiler.
The engine itself is schema agnostic: any MVT dataset works with styles written for it,
for example OpenMapTiles data built with Planetiler, or Shortbread data from VersaTiles
converted to PMTiles.

### Localizing with files of different resolution

The files of a dataset are combined by resolution. Each tile comes from the most
detailed file containing it, and zoom levels missing from all files are cut from the
nearest ancestor tile. A server can thus hold global data with few zoom levels and the
local region in full detail:

| Files | Size (build 20261017) |
|---|---|
| `planet.pmtiles`, zoom 0-15 | 139 GB |
| `world-z8.pmtiles`, zoom 0-8 | 559 MB |
| `nordic-z15.pmtiles`, lon 4...33, lat 54...72, zoom 0-15 | 10.2 GB |

`world-z8` + `nordic-z15` serve the Nordic countries exactly like the planet does, and
the rest of the world with less detail at city scale. Any combination of regions works;
when files overlap, the more detailed one wins, then the smaller one.

### Versioned file names

Files whose names differ only by a version suffix of at least eight digits after `-`,
`_` or `.` are versions of the same file, and only the newest one is used:

```
protomaps/planet-20261017.pmtiles    ignored once the next version is in place
protomaps/planet-20261117.pmtiles    used
```

A single file directly in the data directory gives its dataset the name without the
suffix (`planet-20261117.pmtiles` is the dataset `planet`). New versions can thus be
installed next to the old ones, and the old ones deleted once every server has switched,
which is what makes updates safe on NFS (below). Deleting the newest version switches
back to the previous one.

### Network file systems

Files on local disks are memory-mapped. Files on network file systems (NFS, CIFS, FUSE,
Ceph, Lustre, GPFS, AFS) are read with `pread` instead (`file_access = "auto"`), because
a file replaced on an NFS server disappears from under the clients which have it open:
with a mapping the next access kills the server with `SIGBUS`, with `pread` it is an
ordinary error (`ESTALE`). The engine then rescans the data directory, opening the file
again by its name, and retries the request once. The NFS client still caches the file
pages, and the engine caches the decompressed tiles, so `pread` costs about the same as
a mapping (see §7).

With a read-only NFS mount the update tool runs on the machine which exports the data,
with versioned file names (`-V`). It deletes the previous version only after a grace
period (`-k`, 2 days by default), by which time every server has switched to the new
one at a rescan:

```bash
smartmet-osm-update -d /export/osm -V            # protomaps/planet-20261017.pmtiles
smartmet-osm-update -d /export/osm -V -m extract -n nordic -z 15 -b 4,54,33,72
```

Without versioned names a server which has the replaced file open gets `ESTALE` on its
next read of a tile not in its caches and then reopens the file, so a request may fail
during an update.

### PostgreSQL

The datasets can also be stored in PostgreSQL. This suits sites which already replicate
PostgreSQL to the servers, and makes updates transactional:

* A version of a dataset is loaded file by file, each file in one transaction, and
  published in one transaction. The servers switch to the published version at their
  next rescan, and queries in progress finish with the version they started with.
* The database can be read-only for the servers, for example a streaming replica.
* Old versions can be kept for a rollback, publishing one again switches back to it.

The cost is space and load time: the tiles of a version take about as much space as the
PMTiles file (identical tiles are stored once, as in the file), and loading runs at about
80 MB/s, half an hour for the planet. Every replica receives the whole version.

```bash
DB="host=db dbname=osm user=osm"
smartmet-osm-pgload --db "$DB" --dataset protomaps --version 20261017 \
    world-z8.pmtiles nordic-z15.pmtiles      # load an unpublished version
smartmet-osm-pgload --db "$DB" --dataset protomaps --version 20261017 --publish
smartmet-osm-pgload --db "$DB" --list
smartmet-osm-pgload --db "$DB" --dataset protomaps --prune 1   # keep the previous version
```

The files of a version become its sources named after the files (without a version
suffix), and they are combined by resolution like the files of a directory. Database and
directory sources of the same dataset name are combined too, so a server can add a local
detailed file to a global dataset in the database. The schema (`osm` by default):

| Table | Contents |
|---|---|
| `sources` | One row per loaded file: dataset, version, source, zoom levels, bounds, compression, metadata, size |
| `datasets` | The published version of each dataset |
| `tiles_<id>` | `tile_id`, `run_length`, `data_id`: the PMTiles directory entries of source `<id>` |
| `tiledata_<id>` | `data_id`, `data`: the tiles as stored in the file (gzip), `STORAGE EXTERNAL` |

The tile ids are the Hilbert curve ids of PMTiles. A tile is the entry with the greatest
`tile_id` not above the requested id whose run covers it. A rendered map fetches all its
tiles with one query, a vector tile request one tile per query. If the database cannot
be reached, the engine keeps the sources it had; the tiles of a published version never
change. Do not drop a version which some server may still use: `--prune` keeps the
published version and the given number of newest others, run it only well after
publishing.

### Updating

`smartmet-osm-update` (installed with the engine) downloads a Protomaps build, verifies
it and moves it into the dataset directory atomically:

```bash
# The whole planet (resumable download, MD5 verified)
smartmet-osm-update -d /smartmet/data/osm

# Extracts cut from the remote build with HTTP range requests; needs the pmtiles tool
# from https://github.com/protomaps/go-pmtiles/releases
smartmet-osm-update -d /smartmet/data/osm -m extract -n world -z 8
smartmet-osm-update -d /smartmet/data/osm -m extract -n nordic -z 15 -b 4,54,33,72
```

A file is replaced only when a new build is available. For data on NFS or in PostgreSQL
see the sections below. Run it weekly (or daily) from cron
or a systemd timer, for example

```
# /etc/cron.d/smartmet-osm-update
17 3 * * 1  smartmet  smartmet-osm-update -d /smartmet/data/osm >> /var/log/smartmet/osm-update.log 2>&1
```

The engine rescans the directories every `rescan_interval` seconds and switches to new
files; requests in progress finish with the old ones. A download of the planet takes about
an hour at 40 MB/s, extracts of the world to zoom 8 and of the Nordic countries a few
minutes. Extracting from a local planet file takes seconds:
`pmtiles extract planet.pmtiles nordic.pmtiles --bbox=4,54,33,72`.

## 3. Configuration

```
directory = "/smartmet/data/osm";        # datasets: subdirectories and *.pmtiles files
styles = "/usr/share/smartmet/osm/styles";
rescan_interval = 60;                    # seconds, 0 disables
min_file_age = 10;                       # seconds before a new file is opened
tile_cache_mb = 512;                     # decompressed tiles
decoded_cache_mb = 1024;                 # decoded tiles used for rendering
leaf_cache_size = 256;                   # decoded leaf directories per file
file_access = "auto";                    # mmap on local disks, pread on network file systems

datasets:                                # optional explicitly named datasets
{
  local: { directory = "/data/osm/local"; };
  test:  { files = ["/data/test/a.pmtiles"]; };
};

postgresql:                              # optional tile database
{
  host = "db"; port = 5432; database = "osm";
  username = "osm"; password = "secret";
  schema = "osm";
  connect_timeout = 10;                  # seconds
  max_idle_connections = 8;              # connections kept open between requests
};
```

The database is listed at every rescan.

A missing directory is not an error: the datasets appear when the data is installed.
See `test/cnf/osm.conf`.

## 4. The API

The interface is virtual, so that plugins do not reference engine symbols and can be
loaded even when the engine is not (the engine is optional). Get the engine with
`std::static_pointer_cast<Engine::OSM::Engine>(reactor->getSingleton("OSM", nullptr))`;
a `dynamic_pointer_cast` would reference the engine's type information.

| Call | Returns |
|------|---------|
| `getDatasets()` | Dataset names |
| `getDatasetInfo(dataset)` | Files, zoom range, bounds, JSON metadata and a `version` which changes whenever the files change |
| `getTile(dataset, z, x, y)` | The most detailed decompressed tile at or above the requested one, with its coordinates |
| `getVectorTile(dataset, z, x, y)` | MVT bytes of the requested tile, cut from an ancestor if needed |
| `renderMap(options, crs, box)` | A `Scene`: SVG elements in pixel coordinates |
| `getStyles()`, `getStyle(name)` | Styles of the style directory; `Style::json()` is the original document for clients |
| `getDataTimestamp(dataset)` | Modification time of the newest file, for ETags |

`MapOptions` selects the dataset and the style and controls the rendering: `labels`,
`icons`, `include`/`exclude` (style layer ids, `*` suffix for prefixes), `zoom` or
`zoomOffset`, `fontFamily`, `margin`, `precision` and `maxTiles`.

## 5. Rendering

`Renderer::render`:

1. **Zoom.** The style zoom is computed like MapLibre does, with 512 pixel tiles, from the
   resolution at the centre of the image measured in Web Mercator metres. Hence widths and
   font sizes in the styles are pixels of the output image. The tile zoom is the integer
   part, reduced if more than `maxTiles` tiles would be needed.
2. **Tiles.** The image is sampled in its own CRS every 16 pixels (4 along the edges) and
   the samples are converted to tile coordinates. This works for any projection, including
   polar and global ones.
3. **Resolution.** The tiles are grouped by the most detailed zoom available for them. When
   a group's ancestor tile also covers tiles taken from a more detailed file, the ancestor
   is clipped to the tiles it replaces, so the two never overlap.
4. **Layers.** Features are filtered and styled per style layer. Geometries are clipped in
   tile coordinates (fills overlap by 1/1024 of a tile to avoid antialiasing seams),
   densified for non-Mercator output, projected, clipped to the image and merged into one
   SVG path per layer and paint combination.
5. **Labels.** Point symbols are collected from all symbol layers and placed last, layers
   higher in the style first and then by `symbol-sort-key`, trying each
   `text-variable-anchor` and skipping colliding labels.

Supported style features: background, fill, line and point symbol layers; expressions
(`get`, `has`, comparisons, `all`/`any`/`none`, `in`, `match`, `case`, `coalesce`,
`interpolate` (linear, exponential), `step`, `zoom`, `geometry-type`, `format`, `concat`,
arithmetic, string functions, `let`/`var`), legacy filters and legacy property functions;
`fill-color/opacity`, `line-color/width/gap-width/opacity/dasharray`, `line-cap/join`,
`text-field/size/font/transform/max-width/letter-spacing/anchor/variable-anchor/offset/
radial-offset/padding`, `text-color/halo-color/halo-width/opacity`, `symbol-sort-key`.

Not rendered: line labels (`symbol-placement: line`), icons (drawn as dots when `icons`
is set), fill and line patterns, `fill-extrusion`, raster, hillshade and heatmap layers.
Unsupported expressions evaluate to null and are reported once on standard error.

Fonts are SVG font families: `Noto Sans Bold Italic` becomes family "Noto Sans" with weight
and style, followed by the fallback `fontFamily`. The server needs the fonts installed for
the scripts it renders.

The `Scene` is renderer neutral: a list of SVG elements (`path`, `text`, `rect`, `circle`)
with attributes, which `Scene::svg()` turns into a document and the WMS plugin embeds
into its products.

## 6. Styles

The engine ships styles for the Protomaps schema, generated by `styles/generate.mjs`
(`cd styles && npm install && node generate.mjs .`):

| Style | Source, licence | Suitability as a background for weather data |
|---|---|---|
| `meteo-light` | Derived from Protomaps light, CC0 | Best general choice: light grey land, pale blue sea, borders, place names, faint major roads |
| `meteo-white` | Derived from Protomaps white, CC0 | Strongly coloured data and print |
| `meteo-dark` | Derived from Protomaps dark, CC0 | Radar, satellite and dark user interfaces |
| `versatiles-positrino` | VersaTiles (Positron lookalike), MIT | Good, the classic data visualization basemap; roads more visible |
| `versatiles-positrino-dark` | VersaTiles (Dark Matter lookalike), MIT | Good for bright data, labels are very dim |
| `versatiles-gray`, `versatiles-gray-dark` | VersaTiles, MIT | Good, neutral grey |
| `protomaps-white`, `protomaps-grayscale`, `protomaps-black` | Protomaps data visualization flavors, CC0 | Usable; full road network and points of interest at city scale |
| `protomaps-light`, `protomaps-dark`, `versatiles-muted`, `versatiles-colorful` | General purpose maps | Too busy: coloured landcover, roads and points of interest compete with the data colours |

The `coastline-*` styles are transparent overlays to draw on top of weather data:

| Style | Content |
|---|---|
| `coastline-black`, `coastline-white`, `coastline-gray` | The sea coastline: the outline of the `earth` (land) polygons |
| `coastline-lakes-black`, `coastline-lakes-white`, `coastline-lakes-gray` | The coastline and the shores of lakes and other inland water (`water` polygons of kind `lake` or `water`) |

The land and water polygons of the Protomaps builds come from the coastline-derived
polygons of osmdata.openstreetmap.de, which are cut into pieces of 1x1 degrees. The cuts do
not show: the tiles join the pieces, and the renderer does not stroke the parts of a polygon
outline that lie outside the tile, so a line layer on polygons draws only the real shores.
The WMS OSM layer can change the colour and the width of the lines with `override`.

Why the meteo styles differ from the general purpose ones:

* Only land, water, subtle landcover, borders, major roads (faint) and place names. No
  buildings, points of interest, minor roads, transit or road labels, which would compete
  with isobands, symbols and numbers.
* The background colour is the sea colour, so that the areas beyond ±85° which Web
  Mercator tiles do not cover look like sea in polar and global projections.
* Place names on one line in English (the local name if there is no English name),
  instead of two lines with the local script.
* Border lines are emphasized for orientation.
* The labels and borders can be drawn above the weather data by splitting the style into
  two layers with `include`/`exclude`, see the WMS reference.

Other freely available styles were considered:

* **OpenMapTiles** styles (Positron, Dark Matter, OSM Bright, OSM Liberty, Americana; BSD
  and CC-BY or CC0) need data in the OpenMapTiles schema, for example a Planetiler build or
  the OpenFreeMap planet. VersaTiles' positrino themes give the Positron and Dark Matter
  look on Protomaps data without a second dataset.
* **VersaTiles Shortbread** styles (colorful, graybeard, neutrino, eclipse) need Shortbread
  data; the VersaTiles style library generates the same themes for the Protomaps schema,
  which are shipped here.

Most published styles are designed as maps, not as backgrounds: they emphasize roads,
places of interest and colourful land use. The meteo styles exist because of that.

## 7. Performance

Rendering times on the Protomaps planet (build 20261017, 139 GB on NVMe) with the render
tool: cold = first render (tiles read, decompressed and decoded), warm = rendering again
with the tiles in the engine caches. The WMS plugin adds rasterization (cairo) and its own
image cache on top.

| View | CRS | Size | Zoom | meteo-light cold / warm | protomaps-light cold / warm |
|---|---|---|---|---|---|
| World | EPSG:4326 | 1200x600 | 1.2 | 21 / 11 ms | 17 / 8 ms |
| Europe | EPSG:3035 | 1000x913 | 3.3 | 109 / 9 ms | 118 / 20 ms |
| Scandinavia | EPSG:3067 | 800x847 | 4.1 | 49 / 12 ms | 34 / 8 ms |
| Finland | EPSG:3067 | 600x1011 | 4.8 | 29 / 4 ms | 32 / 4 ms |
| Helsinki region | EPSG:3067 | 1000x727 | 8.5 | 56 / 9 ms | 91 / 42 ms |
| Helsinki city | EPSG:3067 | 1000x667 | 11.7 | 30 / 3 ms | 45 / 10 ms |
| Tokyo | EPSG:3857 | 1000x625 | 8.9 | 9 / 3 ms | 33 / 15 ms |
| New York City | EPSG:3857 | 800x800 | 11.6 | 10 / 3 ms | 25 / 11 ms |

The global + regional files of §2 perform alike; outside the detailed region city scale
maps use overzoomed zoom 8 tiles, which are smaller.

Storage backends, `world-z8` + `nordic-z15` (meteo-light, render tool, PostgreSQL 15 on the
same machine, files and database in the page cache). Cold = first render, warm = the mean
of the next three:

| View | Size | mmap cold / warm | pread cold / warm | PostgreSQL cold / warm |
|---|---|---|---|---|
| World, EPSG:4326 | 1024x512 | 11 / 5 ms | 10 / 5 ms | 14 / 5 ms |
| Finland, EPSG:3067 | 800x1280 | 44 / 10 ms | 42 / 11 ms | 63 / 11 ms |
| Helsinki region, EPSG:3067 | 1024x768 | 44 / 7 ms | 38 / 7 ms | 47 / 7 ms |
| Helsinki streets, EPSG:3067 | 1024x768 | 39 / 6 ms | 39 / 6 ms | 46 / 6 ms |

`pread` costs nothing measurable. PostgreSQL adds a few milliseconds per map with tiles
not yet cached (one query per map), plus the network round trip to a remote database.
Load: 10 GB took 2 min 12 s (the planet about 30 min).

Where the time goes and what was done about it:

* **Projection.** Calling PROJ for each point dominated the rendering time. Each tile now
  gets a 33x33 grid of exactly projected points and the points between are interpolated;
  the grid is verified at the cell centres (at most 0.2 pixel error) and a finer grid or
  exact projection is used if needed, for example near the edges of a projection.
* **SVG output.** Coordinates are formatted from rounded integers without `printf` style
  formatting.
* **Decoding.** Only the layers used by the style are decoded; decoded tiles are cached
  per file, tile and layer set, decompressed tiles per file and tile.
* **I/O.** Files on local disks are memory mapped and the kernel page cache keeps the hot
  tiles; a planet needs no more RAM than the tiles actually used. Database sources fetch
  the tiles of a map with a single query.

## 8. Known pitfalls

* **Never overwrite a mapped file in place.** Truncating or rewriting a file the engine
  has mapped crashes the server with `SIGBUS` on the next access to the lost pages. Install
  new files with a rename (the update tool does), the old inode stays valid until the
  engine drops it.
* **Do not force `file_access = "mmap"` on NFS.** Deleting a file on NFS does not keep
  the mapping valid the way local file systems do, and the same `SIGBUS` follows. The
  default `auto` detects network file systems; a file system it does not recognise as one
  can be handled with `file_access = "pread"`.
* **Do not delete a file still in use over NFS.** Use versioned names and a grace period
  (`smartmet-osm-update -V`).
* **Do not drop a database version still in use.** Publish, wait for the servers to
  rescan, then prune.
* **The style must match the tile schema.** A Protomaps style shows nothing on
  OpenMapTiles data and vice versa; check `vector_layers` in the dataset metadata.
* **Fonts.** Labels in scripts without installed fonts render as boxes.
* **Web Mercator limits.** The tiles end at ±85.05°. The meteo styles paint the
  background with the sea colour; other styles show their background colour there.
